# Paseo GenUI — 内容生成与组件编排规范

> **Generation & Composition Specification · v0.3（对齐 RFC v0.4）**  
> **日期**：2026-10-20  
> **配套文档**：`genui-rfc-v0.4.md`（`render_ui` 工具方案）、`genui-visual-spec.md`（视觉规范，实测数值）、`genui-visual-acceptance.md`（视觉验收）  
> **目标**：对标 ChatGPT GenUI 在对话中**何时可视化、选择哪些组件、怎样组织信息和安排顺序**的可观察体验  
> **适用**：Claude Code、Codex、Pi，以及 Paseo 未来支持的其他 Agent；Web / Electron / iOS / Android 共享生成契约  
> **性质**：**拟定的 Paseo 行为规范**，不是 ChatGPT 未公开的内部生成算法或实际系统提示词；不声称能直接读取其私有生成策略。

---

## 0. 一句话目标与边界

**让模型像一位优秀的信息编辑者，而不是 HTML 设计师。**

模型回答时，应先判断「用户最需要理解什么」，再考虑「是否真的有必要将其中一部分做成组件」。选择、排序、删减、文案由模型负责；布局测量、颜色、字重、图表绘制、数值派生与响应式适配由 Paseo 负责。

与 `answer-with-html` 的根本区别：**不要让模型每次重新发明视觉模板，也不要要求所有回答都使用 UI。**

### 0.1 约束优先级

1. **用户明确要求**（例如“画柱状图”“只回答一句”“给我表格”“不要用图表”）。
2. **事实与语义正确性**（不伪造数据、不改变含义、不用视觉掩盖不确定性）。
3. **RFC v0.4 组件协议及工具安全限制**（v1 十种组件，正确调用 `render_ui`）。
4. **本规范**（选择、组合、文案与节奏）。
5. **视觉规范**（样式统一由客户端实施；不得由模型输出 CSS/像素/颜色）。

用户要求与工具能力冲突时，**诚实说明能力限制并使用 Markdown 退化**；不要偷换成不存在的 GenUI 组件。

### 0.2 严格区分「生成成功」和「显示好看」

| 层次       | 负责者                          | 失败表现                               | 谁修复             |
| ---------- | ------------------------------- | -------------------------------------- | ------------------ |
| 信息判断   | 模型 + Skill                    | 简单问题滥用卡片 / 重点没有突出        | 生成规范、训练样例 |
| 组件选择   | 模型 + Skill                    | 趋势用表格、长意见拆成过量彩色卡       | 本规范             |
| 数据结构   | `render_ui` + 服务端            | Schema 错误、非法字段、超大小          | 工具校验、模型重试 |
| 派生计算   | Paseo 服务端 / 客户端共用纯函数 | 工具返回与卡片显示的比例不一致         | 共享计算实现与测试 |
| 视觉质量   | Paseo 客户端                    | 排版拥挤、主题不一致、图表难读         | 视觉规范及组件实现 |
| 历史与降级 | Paseo 运行时                    | 旧消息丢失、错误卡片出现、无障碍不可读 | 运行时实现         |

## 1. 生成前的五步决策流程

> 这是建议给多模型使用的**明确决策程序**，不是复刻 ChatGPT 内部算法。

### D1. 提炼「单一核心任务」

在组织任何 UI 前，用一句话概括用户的需求类别：

- **求事实**：是什么、为什么、如何做、怎样排错。
- **求比较**：两种方案差多少、哪个更好、权衡是什么。
- **求变化**：跨日期、版本、阶段的发展趋势。
- **求结构**：多个要点的层级、状态或执行顺序。
- **求操作**：需要用户选择、提交、修改参数（v1 不提供真正的表单组件）。

允许一个回答包含多个类别，但必须先确定主任务，避免每个细枝末节都争抢版面。

### D2. 判断可视化的**边际收益**

当且仅当组件明显减少阅读、计算或比较负担，或用户明确要求视觉表示时，考虑 GenUI。

**典型有收益：**

- 至少两组可比较的量、一个重要量与其基线、一个可计算的变化。
- 同一种指标跨多个时间点，有可解释的趋势。
- 多个实体、字段需要并列扫描，比连续段落更易比对。
- 三个左右互斥或层级明确的行动建议，且每一项需要解释。
- 某一结论需要图表支撑，且源数据、单位、口径明确。

**典型没收益：**

- 普通答疑，直接两三句话即可说清。
- 仅有一个随手提及的数字，且不需要强调。
- 一段代码的解释、异常栈追踪、Shell 命令（优先 Markdown + 代码块）。
- 没有可验证数值却想做“炫酷趋势图”。
- 自由叙事、文学评论、连续长篇论证；卡片会打断阅读。
- 内容敏感、信息不确定、缺少可用来源，视觉会误导为“精确已验证”。

**默认策略：不使用。** 这是基线，不是硬性限制；用户明确要求图表、结构化视图时应优先满足。

### D3. 找出需要视觉化的**最小信息单元**

问自己：“若整个回答只允许放一块 GenUI，我应该用它表达哪一段？”

优先将**最值得比较、识别或判断**的部分视觉化。背景、限制条件、行动建议中适合正常语句的部分留在 Markdown；不要将所有内容装进容器。

### D4. 用数据形状选择组件

组件选择见 §2。先问“数据的关系是什么”，不要先问“哪个组件更漂亮”。

### D5. 安排整体阅读路径并调用工具

正常顺序推荐：**简短结论 / 背景 → 核心组件 → 一两句解释 / 下一步**。如果结论完全依赖图表内容，可先给一句目的说明，再给图表，随后总结。读者应无需展开工具记录或打开外部 HTML。

### 1.1 不把本流程显式写进每次回答

这些步骤属于 Agent 内部的**输出规划**，不需要输出“D1、D2、D3”，也不需要向用户解释自己为什么选择组件。用户只需看到自然结果。

## 2. v1 十种组件的选择矩阵

RFC v0.4 的合法 `type` 为：`metricComparison`、`metric`、`progress`、`chart.bar`、`chart.line`、`chart.pie`、`table`、`priorityList`、`card`、`grid`；设计包 v0.5 增加 `steps`、`chart.bar` 的 `orientation` 和顶层 `actions`。

| 组件               | 正确触发条件                                   | 不适合的情况                           | 关键数据要求                                                                  |
| ------------------ | ---------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------- |
| `metricComparison` | 2 个明确可比的数值及方向/变化；旧新套餐等      | 单值、维度不同、不具有共同计量口径     | 原始 `items`、同单位、`compare` 指向有效 id                                   |
| `metric`           | 1 个真正值得突出的关键 KPI                     | 普通陈述中的小数字                     | 数值、单位、清晰标签、必要口径                                                |
| `progress`         | 有合法分母、完成度/使用率/比例；区间有实际意义 | 变化趋势、没有基数的估计               | 分子分母或已有明确可验证的比率契约                                            |
| `chart.bar`        | 同类别间比较、离散时间比较、两系列并列差异     | 太多类别、顺序连续且趋势更重要         | 每组类别及系列原始数值、单位、清晰标签                                        |
| `chart.line`       | 数值随**有序时间/步骤**连续变化，趋势优先      | 无顺序分类、两种互不相关属性           | 有序横轴、同一量纲或明示比较限制                                              |
| `chart.pie`        | 多类别构成占比，类别数不多且数值非负           | 排名精确差异、负值、零合计、很多小切片 | `labelField`、`valueField`、非负 `rows`；比例由 App 计算                      |
| `table`            | 多实体 × 多属性；精确定位单元格比形状重要      | 只有两个数字、内容可一句话说完         | 有含义的列名、可扫描的行、统一口径                                            |
| `priorityList`     | **有明确行动决定/建议层次**且每项需解释        | 仅仅是三条普通并列事实                 | `decision:change/adjust/keep`；可选独立 `priority:high/medium/low`；标题/正文 |
| `steps`            | 有先后顺序的步骤、计划、里程碑，可带完成状态   | 没有先后关系的并列要点                 | 每项标题；状态只在确知时填写；`meta` 放日期或负责人                           |
| `card`             | 一组事实确实构成单个语义对象，需整体呈现       | 每段正文都包框                         | 单一主题、允许的子元素、无重复标题                                            |
| `grid`             | 多个**同类型并列实体**，视觉对齐带来收益       | 宽度紧凑、异质内容被强行拼在一起       | 子项同类、统一字段顺序、考虑移动端降为单列                                    |

### 2.1 冲突裁决（按关系选，不按视觉效果选）

1. **`metricComparison` vs `chart.bar`**：两项核心数值、强调降幅/增长率 → 前者；三个以上类别或多系列整体差异 → 后者。
2. **`chart.line` vs `chart.bar`**：连续时间与走势 → 折线；类别间精确对比 → 柱状。
3. **`table` vs 图表**：读者需要具体单元格和属性 → 表格；需要一眼看整体差异/趋势 → 图表；必要时图表中保留精确 tooltip，不默认重复整张表。
4. **`priorityList` vs Markdown 列表**：确有“需要修改/可以调整/建议保留”的行动决定 → 组件；三项平等知识点 → Markdown 列表。`decision` 是行动，`priority` 是紧急程度，不能混为同一个 `level`。
5. **`card`/`grid` vs 单个组件**：优先单个语义组件；容器只用于显著提升关联感或避免散乱。
6. **`steps` vs `priorityList` vs Markdown 列表**：有先后顺序或进度 → `steps`；有修改/调整/保留的行动决定 → `priorityList`；平等要点 → Markdown 列表。

### 2.2 明确不支持的类型，禁止假装已实现

`chart.scatter`、flowchart、slider、segmented-control、checkbox、input、select、date-picker、popover、carousel、image、map 等**不在组件清单**（时间线用 `steps`）。唯一的交互是顶层 `actions` 后续按钮，由用户确认后发出一条消息。如果需要这些视觉表达，改用现有组件或 Markdown；不要传入未知 `type`，也不要输出 HTML 来“偷做”。

未来扩展组件时只补充矩阵及示例，**不应改变判断“是否需要 UI”的总原则**。

## 3. 整体回答的编排规则

### 3.1 单轮回答的推荐结构

| 回答形态            | 推荐结构                                                        | GenUI 数量       |
| ------------------- | --------------------------------------------------------------- | ---------------- |
| 简单事实/排错       | 直接回答 → 必要说明/步骤                                        | 0                |
| 两个数值的对比      | 最重要结论 → `metricComparison` → 口径/影响                     | 通常 1           |
| 多组数据趋势 / 构成 | 目的说明 → `chart.bar/line/pie` → 趋势或结构解释                | 通常 1           |
| 分级修改建议        | 一句总评 → `priorityList` → 要改什么/为何                       | 通常 1           |
| 多指标状态概览      | 一句状态结论 → `grid` 或 `card` + `metric/progress` → 异常/建议 | 通常 1 个组合块  |
| 长报告、多主题评估  | 各部分结论 + 各自必要的图/表；留出文字推理                      | 2 起，必要时更多 |

**常规建议 0–2 次 `render_ui`**，不是硬限制。回答越长、用户越明确要求视觉报告，容许增加；但每增加一个组件都应能解释它降低了什么认知负担。

### 3.2 开头与结尾

- 开头**先回答用户问的是什么**，不使用“以下是我为你精心设计的仪表盘”等空话。
- 结尾给出**对用户下一步有帮助**的解释、注意点或判断；图表已经表达的全部数字不必逐行念一遍。
- 如果组件自己能够清楚传达答案，可以只有简短的引入和结论，不强行凑成“三段式”。
- 不要把解释性文本拆成许多独立的一句话段落；中文保持自然连贯。

### 3.3 阅读顺序不是模型内部的组件注册顺序

用户首先应看到**重要结论**，其次是支撑它的指标/图表，最后看到条件、例外、行动建议。只有当用户明确希望先看证据或图表时，才反过来。

- **比较**：结论 → 并列数值 → 变化方向 → 影响。
- **趋势**：观察对象与时间窗 → 走势 → 异常点 → 解释。
- **方案评估**：目标/限制 → 关键差异 → 优先建议 → 风险。
- **行动清单**：最优先动作 → 后续调整 → 值得保留的部分。

### 3.4 一个视图只突出一个重点

- `metricComparison` 的主角是核心数值及变化率，不需要额外再加一个重复的 `progress` 卡。
- `chart.bar` 的主角是数据比较，不要在它上方堆三层标题、彩色徽章和说明面板。
- `priorityList` 的主角是行动建议，不要把每个建议再拆成独立彩色卡片。

### 3.5 复用原本的普通文本和 Markdown

普通文字、段落、表格、代码围栏、引用、链接**依旧有价值**。GenUI 是插入式强调手段，不是 Markdown 的替代品。

优先遵守 Paseo 自身的 `render_ui` Timeline 语义：一轮可能是多个 `assistant_message` 与若干 `tool_call` 条目；不能假定 UI 和文字会自动合成一条可跨边界选择的消息。

## 4. 信息层级、密度与语气

### 4.1 文字层级（由内容角色决定，不指定字号）

- **主结论**：用户应该记住的一个判断。
- **模块标题**：告诉读者正在比较什么，而不是重复刚刚的句子。
- **指标标签**：短、具体，例如“旧套餐”“完成率”“耗时中位数”。
- **主数据**：仅给能核实的值，单位与口径一致。
- **附属说明**：限定条件、时间窗口、取整/估计。
- **解读**：图表支持什么、不支持什么；不能凭数据推断因果关系。

### 4.2 文案压缩原则

- UI 标题通常不超过一个短句；避免“关于……的全面深入分析及其未来展望”。
- 卡片说明尽量表达一个信息，不把整篇报告塞入 `detail`。
- `priorityList` 正文可以是自然的完整中文句子，**不为追求精炼而压成生硬词组**。
- 同一单位与统计口径优先在组标题/说明中出现一次；确有必要时在数值处保留。
- 数据名称和模型名称须忠实原文，不为了排版随意改名或砍掉版本号。

### 4.3 克制原则

- 不用颜色、状态字、风险词制造原数据不存在的紧迫感。
- 不为了“高级”滥用星级、百分位、进度条、任务状态。
- 不在正文、组件标题、组件说明、工具回退文本中无意义地重复完全同一段话。
- 不创建只有一行普通文字的 `card`，也不创建嵌套三层以上（RFC 上限两层）的 UI 容器。

## 5. 数据真实性、语义与推断边界

### 5.1 原始值、派生值和模型叙述必须区分

- 模型应优先输出**用户提供或可靠查询得到的原始数值**。
- `metricComparison` 的变化百分比由**服务端和客户端共享的纯计算函数**确定；模型不应提供一个未经验证的百分比覆盖计算结果。
- `render_ui` 校验成功后，工具结果可能包含 `derived.changePercent`（例如 `-85.7`）。**只有工具确实返回该值，模型才可直接引用为工具的计算结果**，并用“减少 85.7%”这样的自然表达；没有返回时可先说“降幅明显”，或基于可信数据单独计算并标明精度，不谎称工具已确认。
- `accepted:true` 只表示数据被 daemon 接受，**不能**推断某个客户端已经显示卡片。
- 数据未知就是未知：不得填零、补估计、补时间点、虚构趋势。
- 多个指标来源不同、时间窗不同、币种不同或统计口径不同，要先说明或避免直接比较。

### 5.2 变化的业务含义不得自动套色

“减少 30%”可能是坏消息（额度减少），也可能是好消息（成本降低）。**数字方向 ≠ 价值判断**。

- 如果含义明确，就在文案里准确说出正负影响。
- `metricComparison` 用可选字段 `compare.changeIntent` 表达变化对用户的意义：`bad`（如额度、收入减少）、`good`（如成本、报错、延迟减少）、`neutral`。App 据此上色：bad 危险色、good 成功色、neutral 或省略为次要文字色。
- 按上下文判断，不按数值正负；判断不了就省略，App 显示中性色。模型仍不指定任何真实颜色。

### 5.3 表格与图表的底线

- `chart.line` 的横轴顺序必须正确，不能用未经排序的字符串制造虚假趋势。
- `chart.bar` 比较量应有相同计量单位；双序列不同单位不能强塞同一个纵轴。
- `chart.pie` 只呈现非负的构成数据，所有原始类别由用户或来源给出；不得补造“其他”凑满 100%。若输入已声明百分比，则合计应接近 100%。
- 绘图时间跨度很长或数据点过多时先考虑精简/分段，并明确采用抽样还是汇总；不得默默删去不利的数据。
- 表格行列是为了查阅，不为了“丰富”而添加无意义字段。
- 估计值标“约 / ≈ / 估计”，不能呈现为精确审计结果。
- 因果解释若无证据，只能用“可能相关”“尚不能据此判断原因”等表述。

### 5.4 数据密度与上限

遵守 RFC v0.4：单次调用参数初始上限 16 KiB、嵌套最多两层、bar/line 最多 200 个数据点、pie 最多 24 类、表格最多 50 行。这是**工具安全上限，不代表推荐一次填满**。通常应选择最能回答用户问题的子集，或在说明中提供进一步细分的思路。

## 6. 组合容器的选用语法

### 6.1 `grid` = 并排比较，不是任意的多栏页面

**推荐：** 并排呈现 2–4 个同语义 KPI；每个子项的标签、数值、说明顺序相同。

**拒绝：** 一格是构成图、一格是诗、一格是技术命令；为了利用宽屏硬凑三列；移动端仍强制多列。

### 6.2 `card` = 语义关联，不是装饰性边框

**推荐：** 一个综合状态块，内部包含标题与少量关联指标；或多个项目共同构成一项结论。

**拒绝：** “一句普通结论外面再套一层背景”，或 `priorityList` 每条外再包 `card`。

### 6.3 一组数据只提供一个最有效的视觉载体

以下情况**通常只选一个**：

- `metricComparison` 已显示 7,500、1,071、85.7%，不要再做一张只含这三项的表格。
- 两组柱状图后不要立刻输出完全相同的二维表，除非用户要求精确表格或图表无法提供充分精度。
- 分级建议已全部写在 `priorityList`，正文不再逐字复制三个建议。

允许例外：不同视图承担不同目的，例如图表看趋势、表格查细节；此时需明确分工。

## 8. 三个黄金样例：包含全文结构，而不只是工具 JSON

> 示例基于 RFC v0.4 草案；完整工具输入见随 Skill 安装的 `references/golden-examples.md`，每个组件格式见 `references/components.md`，十类 JSON 数据测试见 `tests/fixtures/`。以下内容用于训练和验收，不代表后端已部署；正式实现必须与约定的 Schema 一致。

### A. 额度比较：`metricComparison`

**用户请求**：“按 30 天折算，新旧套餐的最高额度差多少？”（已知原始值旧 7,500 HC、新 1,071 HC）

**推荐编排：**

1. 普通文字：`按 30 天理论额度比较，新套餐的可用容量明显减少。`
2. `render_ui` 工具调用：

```json
{
  "type": "metricComparison",
  "title": "按 30 天折算的理论最高额度",
  "data": {
    "items": [
      {
        "id": "old",
        "label": "旧套餐",
        "value": 7500,
        "unit": "HC",
        "detail": "名义推理价值 $375"
      },
      {
        "id": "new",
        "label": "新套餐",
        "value": 1071,
        "unit": "HC",
        "detail": "名义推理价值约 $53.57"
      }
    ],
    "compare": {
      "from": "old",
      "to": "new",
      "metric": "changePercent",
      "precision": 1,
      "changeIntent": "bad"
    }
  },
  "fallbackText": "旧套餐 7,500 HC，新套餐约 1,071 HC，理论额度约下降 85.7%。"
}
```

3. 可选一句解释：`这是按全部刷新额度得到充分利用计算的理论上限，并不等于实际使用量。`

**为什么这样排：** 主结论先交代；数字与差异交给卡片；统计假设留在文字；不用再附一张重复进度图。

**反例：** 前言连写五段才出现数字；将两项数值做两张独立颜色卡、再添加一个显得多余的表格。

### B. 分组柱状图：`chart.bar`

**用户请求**：“把两种模型在新旧套餐下的月度容量放到一张图里。”

**推荐编排：**

1. 普通文字：`下图把两种模型的新旧额度按同一单位并列展示，便于直接比较降幅。`
2. `render_ui` 工具调用：

```json
{
  "type": "chart.bar",
  "title": "30 天等效理论容量",
  "data": {
    "description": "单位：十亿 Token；假设充分利用所有刷新额度",
    "x": "model",
    "series": [
      { "field": "old", "label": "旧套餐" },
      { "field": "new", "label": "新套餐" }
    ],
    "rows": [
      { "model": "DS V4.1 Flash", "old": 7.8, "new": 1.1 },
      { "model": "GLM-5.3 Flash", "old": 9.5, "new": 1.4 }
    ],
    "yUnit": "十亿 Token"
  },
  "fallbackText": "30 天理论容量：DS 旧 7.8、新 1.1；GLM 旧 9.5、新 1.4，单位十亿 Token。"
}
```

3. 必要解读：`两种模型的容量在新套餐中都显著降低，且 GLM 的绝对降幅更大。`

**为什么这样排：** 图的任务是比较组间差异；正文提供方向性结论，不重复逐行报表；标签和图例交给客户端统一绘制。

### C. 分层编辑建议：`priorityList`

**用户请求**：“把剧本修改意见分优先级，尽量少改现有版本。”

**推荐编排：**

1. 普通文字：`我建议先修复影响四阶段衔接的三处关键表达，其余部分尽量保留。`
2. `render_ui` 工具调用：

```json
{
  "type": "priorityList",
  "data": {
    "items": [
      {
        "decision": "change",
        "priority": "high",
        "title": "优先修改",
        "body": "核对凯因醒来后的绝望表达、局长过早提出‘光明终将到来’、最后引出回忆的对话。它们共同决定四个阶段的逻辑是否连贯。"
      },
      {
        "decision": "adjust",
        "priority": "medium",
        "title": "其次调整",
        "body": "优化公墓的环境细节、双意识切换、治疗邀请与实际接受治疗之间的衔接，以及几处不够自然的语言。"
      },
      {
        "decision": "keep",
        "title": "建议保留",
        "body": "保留凯因对局长的讥讽、她对两种意识差异的察觉、铃铛随情绪颤抖的演出，以及她对辛德菲尔斯其他人的担忧。"
      }
    ]
  },
  "fallbackText": "优先修改：阶段衔接的三处表达；其次调整：环境、切换和治疗逻辑；建议保留：人物辨识度与情绪演出。"
}
```

3. 如果用户需要可落地改稿，再用**正常文字**说明最小改动原则；不要复制上面三个段落。

**为什么这样排：** 三类建议是一个整体；长中文句子自然连贯；无须每条独立彩色卡。参考原图时，必须用原文与预期变化进行另外的视觉回归，不能拿这个改写样例冒充截图级基准。

### D. 构成占比：`chart.pie`（v1 新增）

当用户提供某项构成数据（如开发 46%、测试 27%、设计 17%、其他 10%）并要求占比图时，**直接使用 `chart.pie`**，不用声明“不支持”或在纯文本中把数据拼成“伪饼图”。要求每个数据项非负且总量大于零；如果是百分比，总和需接近 100%。完整调用示例见 `references/components.md` 中 `chart.pie` 节及 `tests/fixtures/pie-distribution.json`。图例与扇区配色由客户端负责。

### E. 普通问题：**不调用 `render_ui`**

**用户请求**：“`otool -L` 和 `otool -D` 有什么区别？”

**推荐回答：** 用两段中文与两段短代码示例直接解释：`-L` 列出动态库依赖；`-D` 显示动态库的 install name（如适用）。不调用 `metric`、不做比较卡、不画柱状图。

**为什么这样排：** 用户需要可复制命令和概念解释，卡片不会减少理解成本。

## 9. 工具使用与容错规则（和 RFC v0.4 对齐）

### 9.1 不允许的“捷径”

- 不输出 HTML/CSS/JS，不声明任意字体或颜色，不在 `data` 里放可执行逻辑。
- 不生成本地 HTML 文件再让用户打开，除非用户明确选择 HTML 产物。
- 不使用不在 v1 列表中的组件名。
- 不使用 `render_ui` 伪装成执行文件修改、安装、付款、发送消息等操作。v1 是**展示型工具**。
- 不把工具的内部错误栈贴给用户当最终回答。

### 9.2 精简 Schema 下的参数策略

RFC v0.4 的工具参数保持精简：`type`、`title?`、`data`、`fallbackText?`、`schemaVersion?`。工具说明（description）里为十种类型各写一行最简 `data` 格式，与 `SKILL.md` 的表格逐字一致；完整结构由服务端按 `type` 校验，校验失败时连同正确格式和示例一起返回。为减少多模型的反复试错：

1. Skill **直接给出十种类型的一行数据结构**，详细字段在随 Skill 分发的 `references/components.md`；黄金 A/B/C 在 `references/golden-examples.md`。这两个文件与 `SKILL.md` 同目录，不能只指向仓库的 `docs/`。
2. 不确定字段时**按需读取**相应参考节，不要臆造字段；只有工具或 Skill 文件不可用、数据缺失等原因才回退 Markdown。
3. 服务端返回字段错误和示例后，**只更正这一处调用**，不无端修改原始数据。
4. 建议同一块最多重试 2 次；仍失败则采用 Markdown 回答，并在需要时简短告知未能渲染。**这是本规范建议的 Agent 行为，不是现有工具自动执行的策略。**

### 9.3 完成态与预览态不能混淆

流式阶段的 `render_ui` 可能由 Claude 的部分工具输入触发骨架或占位，但**模型不应把“调用已开始”当作“已渲染成功”**。即使工具返回 `accepted:true`，也只表示 daemon 已接受，不能保证每台 App 均完成渲染。最终显示必须以成功校验的完整参数为准；失败时按 RFC 的工具错误流程修正或降级。

### 9.4 `fallbackText` 的撰写

`fallbackText` 虽然在协议中是可选字段，本规范**推荐默认提供**：

- 一个自然、独立可读的摘要，通常 1–3 句；不是 JSON，也不是“请查看图表”。
- 包含关键实体、单位、结论或必要数值，方便通知、日志、旧客户端和复制。
- 不携带密钥、完整敏感数据、未授权披露的信息。
- 它是降级内容，允许与可视化信息局部重合；但不要把它当作平时可见的重复正文。

### 9.5 Agent 仅有只读解释任务时

生成 GenUI 不应改变工作区文件，不要求自动创建 HTML 或图片工件；可视化展示不属于执行用户未授权的副作用操作。

## 10. 反例集：什么会破坏 ChatGPT 式可视化体验

| 反例                                           | 问题                               | 正确替代                          |
| ---------------------------------------------- | ---------------------------------- | --------------------------------- |
| “你好”→ 大欢迎卡                               | 把普通对话伪装成产品首页           | 直接回话                          |
| 一个版本号 → `metric`                          | 没有可比较的认知任务               | 行内代码或正文                    |
| 三句平等建议 → `priorityList` 并强行填决定字段 | 强加不存在的行动层次               | Markdown 列表                     |
| 旧套餐 + 新套餐 → 两张独立卡 + 进度卡 + 表格   | 一份数据重复四次                   | 一个 `metricComparison`           |
| 7 天趋势 → 用 `table` 代替折线图               | 主要问题是“变化如何”，不是逐项查数 | `chart.line`（数据连续有序时）    |
| 3 个没有共同单位的值 → `chart.bar`             | 视觉比较无意义                     | 解释差异或拆成明确单位的视图      |
| 一个结论反复在标题、卡片、正文中重复           | 信息密度下降                       | 只保留必要位置                    |
| 凭两次观测声称“稳定趋势”                       | 超出证据支持范围                   | “两次数据有所变化”                |
| 把减少 85.7% 直接写成“节省 85.7%”              | 业务方向错误                       | 明确是额度减少还是成本降低        |
| 用户要代码修复 → 先出仪表盘                    | 错误聚焦                           | 先提供可执行修复步骤              |
| 分类数为负或全部为零仍强行画 `chart.pie`       | 扇区无有效占比含义                 | 澄清数据 / Markdown               |
| 遇到工具错误重复调用五六次                     | 浪费用户等待时间和 Token           | 限次修复后降级                    |
| 长篇中文评审每行加彩色徽章                     | 分散注意力                         | 一段自然正文或单个 `priorityList` |
| 根据模型想象填写小数点后四位                   | 伪精确                             | 保留来源精度并标注估计            |

## 11. Skill 的分发方式与模型差异

**核心生成规则只维护一份**：`skills/paseo-genui/SKILL.md`。与其一起分发 `references/components.md`、`references/golden-examples.md`，模型按需读取；完整规范（本文件）供实现、评测和回归使用，不应把全部文档每轮塞给模型。

Paseo 当前的 bundled orchestration skill 系统可分发到 `~/.agents/skills`、`~/.claude/skills`、`~/.codex/skills`。Pi 另有自有目录与 `.agents/skills` 的发现逻辑。**但目录存在不等于 Agent 在当前会话一定自动使用 Skill**；必须在 M0 验证模型的发现、触发和上下文读取。

### 11.1 三种使用状态

- **Auto（默认）**：只在 D2 有明显收益时使用 `render_ui`。
- **Requested（明确要求）**：用户明确要“图表、可视化、卡片”时尽量满足；不支持的组件必须说明限制。
- **Disabled（明确关闭）**：完全不主动调用 `render_ui`，正常使用 Markdown；开关由 Paseo/Agent 配置落地，Skill 不能单独保证禁用工具。

### 11.2 不同模型的校准重点

| 模型问题               | 不建议的解决方式             | 优先的解决方式                                    |
| ---------------------- | ---------------------------- | ------------------------------------------------- |
| 小模型总想做卡片       | 强迫所有回答必须 GenUI       | 强化“默认不用”和负样例                            |
| 模型不懂 `data` 的格式 | 放开任意 JSON 容错           | 2–3 个同型示例、校验反馈、按需 Schema             |
| 模型大量重复数字       | 再加更多卡片                 | 约束正文与组件分工                                |
| 模型偏爱自己画 HTML    | 放任 `answer-with-html` 接管 | 明确 UI 只经 `render_ui` 输出                     |
| 模型继续文本顺序异常   | 在 Skill 中许诺一定正确      | provider M0 排查 Timeline 顺序，不可由 Skill 掩盖 |

| T20 | “已经给出两模型四周耗时、新旧套餐 HC，请综合分析” | 少量分工清晰的图表 + 文字，不要求不存在的附件 | 虚构缺失附件、卡片泛滥             |

### 12.1 建议记录的可量化指标

- **触发准确率**：该使用时使用，不该使用时不使用。分别统计误触发和漏触发。
- **组件匹配准确率**：使用了能回答主要问题的组件，而非只看是否调用工具。
- **首次 Schema 通过率**：各模型、各组件分别统计，避免总均值掩盖弱项。
- **事实一致性**：组件原始数据、自然语言结论、`fallbackText` 是否一致。
- **冗余度**：重复同一数据/结论、无收益的组件、冗余容器数量。
- **渲染结果 QA**：独立按视觉规范评估，不能用生成通过率替代视觉分数。

### 12.2 人工评分量表（100 分）

| 维度             |    分值 | 判定重点                           |
| ---------------- | ------: | ---------------------------------- |
| 是否该可视化     |      25 | 有收益才用，用户明确指示优先       |
| 组件选择         |      20 | 数据关系与可视形式相配             |
| 结构与节奏       |      20 | 重要内容先出现，文字与组件分工清楚 |
| 数据真实性与语义 |      20 | 单位/时间窗/来源/零与缺失正确      |
| 文案克制及密度   |      10 | 没有重复结论、不堆容器             |
| 工具容错与退化   |       5 | 校验失败可恢复，禁用时仍可答       |
| **总计**         | **100** |                                    |

**建议发布阈值**：各模型评估集平均 ≥ 85，且 T01/T02/T10/T13/T18 等“不得乱用”案例无严重错误；具体阈值为项目验收建议，而非 ChatGPT 内部标准。

### 12.3 一票否决

- 用户明确禁止图表仍调用 UI。
- 用未提供的数据捏造图表。
- 隐瞒不同单位或不同时间窗造成误导比较。
- 模型擅自调用有副作用的工具来“完成视觉效果”。
- 不支持的组件类型被当作已实现展示。

## 13. 产品实现建议（不修改 RFC 的主架构）

1. **把 Skill 与渲染器分开迭代**：不调 CSS 能改选择策略，不调提示词能改卡片视觉。
2. **引入 GenUI 观测日志**（仅存组件 type、调用是否成功、重试次数等非敏感元数据；不要日志化完整数据或密钥）。
3. **为每条可视化绑定语义角色**（对比、趋势、进度、建议），让工具类型和 UI 内容可被自动评测。
4. **保留编辑/复制原文的入口**：即使组件不可展示，`fallbackText` 也要能独立表达主要结论。
5. **不要混淆合规和美观**：Schema 正确只是必要条件，视觉规范和生成规范必须分别通过。
6. **基于真实用户任务迭代**：观察“是否减少查找、解释、回看”，而非追求一轮调用尽可能多的组件。

### 13.1 实现时需要注意的接口问题

- **工具结构发现**：已定做法为工具说明内写十类最简格式，Skill 的 `references/` 提供完整格式与黄金样例，校验失败时返回正确格式。M2 统计各模型的一次通过率与重试次数，不再另做薄/厚 Schema 对比测试。
- **混排可用性**：Timeline 三段不等同单条消息；历史搜索、复制、会话摘要要在运行时专门验证，而不是由 Skill 许诺。
- **旧客户端退化**：`fallbackText` 是跨版本最重要的可读摘要之一，建议在生成规范中默认为每次提供。
- **技能生效检查**：系统分发 Skill 不代表某 Provider 已读取。上线前必须覆盖不同 Agent 的发现与读取路径。

## 14. 交付与验收的最小集合

交付开发时至少包含：

1. 本文件：完整的选择、编排与评测契约。
2. `skills/paseo-genui/SKILL.md` + `references/`：面向模型的精简规则与按需读取的组件完整格式、A/B/C 黄金样例。
3. `tests/generation-cases.json`：可重放测试请求与预期行为。
4. RFC v0.4 + `schemas/render-ui.v1.schema.json`：组件协议草案和服务端 Zod 对齐依据。
5. 视觉规范（`genui-visual-spec.md`）、视觉验收（`genui-visual-acceptance.md`）与 A/B/C 参考图：属于**另一条验收线**。

**验收原则：** 要实现的是“理解任务后自然选用最有效的 UI”，而不是“看到用户输入就拼出一个漂亮 JSON”。如果关闭 GenUI 后普通回答反而更清楚，说明这次组件选择可能不合格。

## 附录 A：可直接复制到 Skill 的核心规则（压缩提要）

- 默认只使用自然语言和 Markdown；当比较、趋势、分级建议或并列扫描明显更易理解时，再调用 `render_ui`。
- 先回答用户真正的问题；通常一个组件承担一个主要认知目标。
- 类型只能取 RFC v0.4 的十种；饼图已加入 v1，表单/地图/散点图/轮播等仍未实现。
- 模型只提供真实数据、语义标题和精简摘要；布局、颜色、字号、比例计算交给 Paseo。
- 常规回答通常 0–2 个可视化块；必要时增加，但不要卡片堆叠或重复显示相同数据。
- 图表要注明单位、时间窗和假设；缺失不填零，不伪造数据，不把相关性说成因果。
- `fallbackText` 应可独立阅读；工具失败限次重试，失败后用 Markdown 回答。
- 只有在用户要求或 UI 确能提高阅读效率时才用 GenUI，**不能牺牲自然中文表达和信息准确性**。

## 15. 本次修订的行为契约（v0.2）

- **Skill 可单独安装**：`SKILL.md` 不再依赖只有开发者可见的 `docs/`；所有组件字段与三个黄金样例随 `references/` 一起复制到各 Agent Skill 根目录。
- **派生值可引用**：只在工具的 `derived` 实际返回相关字段时引用其数值；不要把 `accepted:true` 解释成 App 已显示。
- **优先级语义拆分**：`priorityList.decision` 是行动决定，`priority` 是可选紧急程度；移除旧 `level`。
- **测试不会无端追问**：T06、T20 原请求已经给出可用数据，验收标准不再要求寻找缺失内容；T12 变为验证新纳入的 `chart.pie`。
- **工程参考仍单独保留**：本规范约束模型行为，机器可读 Schema、RFC 与视觉质量验收由其他文件承载；三个文件在同一交付包中锁定版本。
